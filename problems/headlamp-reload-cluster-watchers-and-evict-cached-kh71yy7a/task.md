If a context is cached and a request comes in with KUBECONFIG for the same cluster + user, we should replace that context instead of just updating the context's TTL. Otherwise, any changes to servers/credentials/oidc etc. won't take effect. This means we'll need to remove any cached responses, clientset and the watcher if it was created. We should create a new watcher right away rather than wait for another request. This should apply when we're not using the cache as well as if the context has expired but may have watchers/responses etc. Contexts coming from requests should not be available to other users because they belong to the user.

When more than one request comes in with KUBECONFIG while the cluster is configured to use cached contexts, there are some races to think about. If we're stopping a watcher and it's context has a new one from another request, don't clear the new one. If request B replaces request A's context, request A shouldn't save responses or create a clientset. If request B can't parse its KUBECONFIG it isn't setting anything, so it doesn't count as being after request A, and it shouldn't prevent A's context from being used.
