Add a way for custom functions registered on a compiler to receive the context.Context that a query is run with, and a way to reuse a compiled query across multiple runs while overriding what a given custom function does on a per-run basis, without recompiling the query.

Today, a custom function added through the compiler options is a plain Go function of a fixed shape that takes the input value and the argument list and returns a value. It has no way to see the context.Context that the caller passed in when running the compiled code, even though that context is already available internally and is used to support cancellation of the query itself. Two independent users of the library have run into the consequences of this: one wants to look up caller-specific data, backed by a per-request context, from inside a custom function used in an HTTP handler, and another wants to reuse a single compiled query across many runs while varying what a function does from run to run, without paying the cost of recompiling the query or discarding the parsed program every time. Right now neither is possible, because everything about a custom function is fixed once and for all when the query is compiled.

There should be a way to register a custom function whose callback additionally receives the context that the query is currently running with. When the query is run without an explicit context, the callback should receive a background context rather than a nil one. It should be possible to register an iterator-style function (one that can emit multiple values) with the same context-awareness.

Separately, but for the same underlying reason, it should be possible to run an already-compiled query while overriding, for that run only, the callback of a custom function that was registered when the query was compiled. Two different runs of the same compiled query, made concurrently or one after another, must not affect each other's overrides. Overriding a function should only ever affect calls to that function's name in the running query; it must never be able to interfere with how gojq itself evaluates unrelated built-in operations, even if an override happens to reuse an internal name. A per-run override should only take effect for the argument-count range it was registered for, leaving other argument counts of the same function name to whatever was registered at compile time, and attempting to override a name the query never actually calls should simply have no effect rather than causing an error. Existing custom functions that do not need any of this should keep working exactly as they do now, with no change in behavior or signature.
