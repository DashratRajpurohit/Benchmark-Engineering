When gitindex walks a commit's tree to decide which files to index, a subtree it cannot read is treated the same as reaching the end of the tree. The build finishes normally, writes a shard, and reports success, even though part of the repository was never visited, with no error or warning: the shard just holds fewer files than the tree actually contains.

One concrete way this happens: a repository cloned with `git clone --shared`, so most of its objects live only in the origin repository's object store and are reached through git's alternates mechanism. Indexing such a clone should index every file reachable from the requested branch, including files that only exist via an alternate object store, the same as indexing a normal, self-contained clone of the same commit would. Right now it does not, and produces a shard covering only whatever happens to be stored directly in the clone itself.

Fix the walk so it cannot mistake an unreadable part of the tree for having finished normally: if any part of the tree cannot be read for a reason other than genuinely reaching the end, indexing should fail with an error rather than silently publish a shard with fewer files than the tree actually has. Separately, make sure a `git clone --shared` style repository indexes completely and correctly.
